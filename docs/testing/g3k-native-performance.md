# G3K native performance: baseline and candidate comparison

Status: **measured** (Linux, headless browser display). Native WebView2 (Windows) and WebKitGTK (Linux) measurements on the owner's machine remain open.

This report compares the G3J application with the G3K candidate **on the same Linux machine, with the same synthetic fixtures, the same driver and the same cache state**, three repetitions per case. It claims a difference only where the candidate's range does not overlap the baseline's. Raw results (one JSON line per run) are in [`docs/benchmarks/native-performance/g3k/`](../benchmarks/native-performance/g3k/).

The G3G Windows baseline ([g3g-native-performance.md](g3g-native-performance.md)) is a historical measurement of an older commit on different hardware and an older OS. It is **not** compared numerically here.

## Method

**Headless service** (`TestPerfNativeServiceBaseline`, 100k fixture): cold import, incremental restart with 1,000 new events, and 40 live appends measured to the service summary. Checkpoint serialization and SQL commit times and service-mutex wait/hold times come from the counters.

**Whole application** (`scripts/testing/g3k-perf.cjs`, run by `scripts/testing/g3k-perf-run.sh`; 10k-event profile, imported before each case):

| Case | What runs | Window |
| --- | --- | --- |
| `launcher-idle` | `/launcher` open | 300 s after 30 s settle |
| `dashboard-idle` | `/nav/route` open, no events | 300 s after 30 s settle |
| `dashboard-hidden` | `/nav/route`, document reported hidden | 120 s after 30 s settle |
| `live-latency` | 30 FSDJump appends, 700 ms apart; journal write until the page shows the new system | per event |
| `fsd-transitions` | `/ship/status`; 20 cycles of 8 Status updates (250 ms) through charge, then StartJump and FSDJump | about 70 s |
| `tab-switch` | client-side route changes over Commander, Fleet, Biology, Ship status and Route, 3 rounds; route push until the page's data frames settle (300 ms quiet) | per switch |
| `paired-1-same`, `paired-2-same`, `paired-2-different` | main display plus 1–2 paired displays (same page, or Route and Ship status); 120 s with Status every second and a jump every 10 s | 120 s |
| `resume-reconnect` | `/nav/route` hidden for 60 s while 6 jumps arrive, then visible: time to the newest system; then the page's sockets are closed (the client reconnects by itself) with one jump meanwhile: time to fresh content | per transition |

CPU is user+system time from `/proc/<pid>/stat` for the host process and for every process in the browser's process tree. Memory is the proportional set size (PSS, `smaps_rollup`), so shared pages are not double-counted. Socket frames and bytes are counted on the browser side. Builds, encodings and lock times come from the host counters.

**Hidden emulation.** Headless Chromium does not report background tabs as hidden, so `dashboard-hidden` and `resume-reconnect` override `document.visibilityState` and dispatch `visibilitychange`. This reproduces everything ERIDION's JavaScript and host do for a hidden document, but not the browser's own paint suppression. Browser CPU in these cases is an upper bound; host CPU, frames and builds are the meaningful measures.

## How to read the results

- Values are **mean (min–max) over three repetitions**.
- A difference is claimed only when the ranges do not overlap. Otherwise it is reported as "no measurable difference".
- `base` and `cand` ran **interleaved** in one session on a quiet machine (`docs/benchmarks/native-performance/g3k/final/`). There are two exceptions:
  - The baseline 5-minute `launcher-idle` and `dashboard-idle` runs come from the Phase A baseline (`phaseA-baseline/`). That session used the same machine, binaries and 300 s windows, but development work was running at the same time.
  - `cand-lowlatency` ran as a separate, later block, so its CPU comparisons with `cand` are less reliable than `base` against `cand`.

**No measurable difference:**

- Idle launcher and dashboard CPU and memory, host and browser. With no events there is little to save, and a visible dashboard still builds its navigation context once a second by design.
- Host CPU in the live, FSD and paired cases (ranges overlap; differences of 4–7 %).
- Socket bytes, which overlap or are dominated by one-time snapshots.
- Browser CPU and memory everywhere.
- Event-to-visible latency, whose p50 is 300 ms in both builds: it is bound by the journal reader's poll interval, not processing.
- Reconnect to fresh content: about 5.0 s in both builds, the client's reconnect delay.
- The 100k cold import, incremental restart and checkpoint timings (see PERF-10).

**Trade-off (normal mode is the default):**

- Resume from hidden to fresh content is 18.3 ms (16–20) in normal mode against 10.7 ms (10–11) in the baseline, because deferred domains are built on resume.
- Low-latency mode restores it to 11.7 ms (10–14), at about +2.4 MB host PSS and more domain builds while hidden (resume case: 63 against 34; live case: 150 against 125).

No improvement is claimed beyond the rows above.

## FSD transitions: a note on comparability

In the `fsd-transitions` case the number of `goNavigationContextChanged` frames varies between runs in **both** builds: either about 40 (charge/jump/idle states caught every cycle) or about 21 (jump states never caught).

The synthetic StartJump→FSDJump window is 500 ms, while the context is pushed on the existing one-second cadence. Whether it is sampled therefore depends on the phase alignment between the scenario and the ticker. A dedicated probe that recorded the pushed modes showed both outcomes for both builds (base: 40 and 21; cand: 38 and 21).

This is a pre-existing sampling limit, not a G3K change. Real hyperspace jumps last many seconds, but **event-driven context pushes** would remove the limit and are recommended as follow-up work. FSD frame and byte counts are therefore not compared.

## PERF-10: durable checkpoints (evidence; implementation retained)

From the headless service benchmark's counters (100k cold import, three repetitions, interleaved):

| Measure | base | cand |
| --- | --- | --- |
| Cold import wall time | 10.85 s (8.51–15.02) | 8.68 s (8.51–9.02) |
| SQL commit time, total (400 transactions of ≤256 records) | 6.41 s (5.18–8.68) | 5.36 s (5.29–5.49) |
| Gob serialization of the derived cache (before and after each commit) | 1.16 s (0.84–1.76) | 0.88 s (0.86–0.91) |
| Service-mutex hold, total / max | 9.90 s / 60.7 ms | 7.99 s / 39.7 ms |
| Restart + live phase: SQL commit time, total / max | 133.9 ms (115.5–155.6) / ≤33.5 ms | 117.3 ms (111.9–125.2) / ≤26.8 ms |
| Live append latency p50 / p95 | 349.8 / 357.5 ms | 349.8 / 352.4 ms |

(The baseline's wide range comes from one slow repetition; the ranges overlap, so no import-speed difference is claimed.)

**Findings:**

1. During a cold import, durable SQLite commits take about 60 % of the wall time and run under the service mutex. Serialization takes about 10 %. This is a one-time cost of a few seconds per 100,000 events.
2. In live operation the service mutex's typical hold is microseconds. Its maximum (about 30 ms) coincides with a commit, and live latency is set by the reader's 500 ms poll, not by persistence.
3. No provider was configured, so provider-local preparation was zero here. Measuring it needs a consented provider set-up with synthetic transports; this remains open.

**Decision:** there is no meaningful live-gameplay bottleneck in the checkpoint path, so the implementation is **retained unchanged**. Persistence never moved ahead of publication. A future import-throughput change (for example larger replay transactions) would be a separate durability-scoped batch: it must first define and fault-inject the atomic checkpoint/replay contract (offsets, source events, derived cache, consent, receipts and publication rolling back together) before any change.

## Map interaction

No signed Galaxy Painter data is installed on this host, and downloads need consent. Whole-application map interaction was therefore **not** measured. PERF-07 to PERF-09 are covered as follows:

- **PERF-07:** a complete viewport is confirmed with a small `unchanged` reply instead of resending coordinates, and the client stops polling once the viewport is ready (`TestPerfSpatialPlanningAndCache`; the G3E/G3D gates count spatial requests).
- **PERF-08:** the planning benchmark above. Planning decodes zero blocks, overlapping viewports reuse decoded blocks (counter-verified), and the decoded cache is bounded at 24 MiB.
- **PERF-09:** paint coalescing, buffer reuse and exact pixel placement are verified in `tests/service/g3k-canvas.test.js` and the g3c/g3d/g3e browser gates. No main-thread measurement justified workers or OffscreenCanvas, so none were introduced.

A map-interaction measurement with installed signed data on the owner's machine remains open.

## Limitations

- Linux and headless Chromium only. There is no native WebView, no Windows, and no GPU compositor comparable to the desktop window.
- Hidden emulation reproduces the application's behaviour but not the browser's own paint suppression (see Method).
- Paired displays ran on the same host (loopback HTTPS), not on separate devices.
- p50/p95 values from host counters are log2 bucket upper bounds. The tables report means and maxima, plus browser-side latencies measured directly.
- Measurements are synthetic. Real-game acceptance is listed in the G3K ledger.
