## Method

**Headless service cases** — [`TestPerfNativeServiceBaseline`](../../go/internal/webapp/perf_baseline_test.go) (skipped unless `ERIDION_PERF_JOURNAL` is set) runs the real embedded service in-process: journal reader, SQLite writer, reducers, workspace/parity/exploration projections and provider wiring, without a window. One run = one repetition of:

1. **Cold import**: start on an empty profile, wait until the summary reports the import finished with all events read. Wall time, process CPU time (`GetProcessTimes`, user+kernel) and peak working set (`GetProcessMemoryInfo`).
2. **Incremental restart**: append a new journal file with 1,000 events, restart on the same profile and wait until the last new system is current and the import finished.
3. **Live append latency**: append 40 single FSDJump lines (150 ms apart) to the active journal and time the write until the service summary reflects the event (the first host-side point every display reads; socket delivery and paint are **not** included).

Command (from `go/`): `go test -c -o webapp.test.exe ./internal/webapp` then `ERIDION_PERF_JOURNAL=<100k fixture> webapp.test.exe -test.run TestPerfNativeServiceBaseline`.

**Whole-app launcher idle** — [`scripts/testing/native-idle-sample.ps1`](../../scripts/testing/native-idle-sample.ps1) starts `daedalus.exe --data-dir <temp> --journal-dir <10k fixture>`, waits 60 s (import and launcher load), then samples every 5 s for 300 s the CPU time and working set of the app **and every descendant process** (the WebView2 browser, GPU, utility and renderer processes). The launcher window was open and visible; no dashboard window, no paired device.

Three repetitions per case, run back to back with 10 s pauses.

## Results (three repetitions)

### Headless service, 100k-event fixture

| Measure | Mean | Min | Max | Runs |
| --- | --- | --- | --- | --- |
| Cold import wall time | 16.27 s | 16.10 s | 16.60 s | 16.60 / 16.10 / 16.10 |
| Cold import CPU time | 19.63 s | 19.19 s | 20.23 s | 19.45 / 20.23 / 19.19 |
| Peak working set (whole run) | 35.7 MB | 35 MB | 37 MB | 35 / 35 / 37 |
| Profile size after import | 165.3 MB | 165.1 MB | 165.4 MB | |
| Incremental restart (+1k events) wall | 0.837 s | 0.831 s | 0.846 s | |
| Incremental restart CPU | 0.55 s | 0.47 s | 0.61 s | |
| Live append → summary, p50 | 349.7 ms | 349.6 ms | 349.8 ms | |
| Live append → summary, p95 | 367.7 ms | 364.9 ms | 371.8 ms | |
| Live append → summary, max | 510.2 ms | 505.8 ms | 514.6 ms | |

Interpretation notes:

- Live-append latency is dominated by the journal reader's **500 ms poll interval** (`journal/reader.go`); the fixed 150 ms write spacing phase-locks to that cycle, which is why p50 is so stable. It measures detection cadence, not processing cost. A change-notification reader or a different cadence would show up here first.
- Peak working set is the in-process Go service only (test binary); SQLite file cache is OS-managed and not included.

### Whole-app launcher idle, 10k-event profile (app + WebView2 children)

| Measure | Mean | Min | Max | Runs |
| --- | --- | --- | --- | --- |
| CPU time over 300 s | 15.74 s | 15.11 s | 16.84 s | 15.25 / 16.84 / 15.11 |
| Average CPU (% of one logical core) | 5.22 % | 5.02 % | 5.59 % | |
| Working set, start of sample | 427.3 MB | 426.4 MB | 428.8 MB | |
| Working set, end / max | 429.0 MB | 428.4 MB | 430.2 MB | |
| Processes in tree | 8 | 8 | 8 | of which 6 WebView2 |

Working-set growth during the 5-minute window was below 4 MB in every run, measured from the reading taken right after the 60 s warm-up. Measured from the first 5 s sample instead, growth was up to 8.4 MB (run 1: 421.8 → 430.2 MB). Windows working set is not the same measure as Linux RSS or private bytes. The launcher idles at about 5 % of one core; where that CPU goes (Go service polling vs. renderer timers such as the launcher's 5 s `getGoLauncher` poll and the clock) was not attributed in this baseline.

## Scope of this baseline (audit F10, 23 November 2026)

- The binary measured is `dbe3de1`. Later commits on the branch (journal-rank resolution, account epochs and connection scopes, Exosuit history retention, default-commander validation) were not re-measured. A candidate comparison must re-measure the baseline head and the candidate on the same machine.
- Only Windows was measured. The fixture hashes above reproduce exactly on Linux with the generator (checked 23 November 2026); no Linux timing was taken.

## Not measured in this baseline

These plan cases need a driven dashboard window, a second device or instrumentation that does not exist yet; they remain open for the next measurement step and must use the same machine:

- dashboard idle and tab-to-fresh-content; event-to-visible latency including socket delivery and paint (p50/p95);
- map interaction, stationary/interactive spatial requests, renderer memory under map use;
- one and two paired displays (same and different views), minimize/resume/reconnect/revoke;
- large Fleet/loadout pages, biology/FSD/route transitions;
- socket frame/byte counts, query/decode counts, lock hold times, checkpoint writes;
- Linux.
